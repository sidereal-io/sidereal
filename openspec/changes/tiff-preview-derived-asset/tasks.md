## 2. Core records previews [depends-on: 1]

- [ ] 2.1 [complex] `run_operator` gives the Operator a staging `Output` that begins staging on the first write, then checks, publishes and commits a proposed preview in `store`'s transaction: a new Asset with `origin` `derived`, the proposed kind and the input Asset's name; its version with core's BLAKE3 hash and size, the proposed media type and the Operator's id and version as `source_id` and `source_version`; and one `asset_lineage` row with role `preview` and the run's id. New tests in `core/src/operations/derives.rs`, using `fixture.rs` and `Scripted` Operators with `makes_previews`, cover every scenario of derived-assets "Core checks a proposed preview before it stores it" and "Core records a preview as a derived asset with lineage", with these reasons: `operator <id> does not make previews`, `a preview cannot be image/tiff`, `the preview is empty`, `the preview is larger than 100 MiB`; each failure leaves no new Asset, version, lineage row or file in the storage folder's `tmp`, and a refused facet stores neither the facet nor the preview. A cancel after the write, and a refused commit, leave no Asset, version or lineage row (design decision 2) — needs the database fixture (verify: `cd server && deli -- cargo test -p sidereal-core -- operations::derives`, then `deli -- cargo test -p sidereal-core -- operations`)

## 3. The image pack reads TIFF and makes previews [depends-on: 1]

- [ ] 3.1 [easy] The manual-upload Source accepts bytes that start with `II*\0`, `MM\0*`, `II+\0` or `MM\0+` as an `image` of media type `image/tiff`, and its refusal reads `only PNG, JPEG and TIFF images are supported` for GIF, SVG, empty bytes and plain text; tests in `packs/image/tests/recognition.rs` cover the four signatures and the refusals (design decision 4; image-upload "Image recognition uses the bytes") (verify: `cd server && deli -- cargo test -p sidereal-pack-image --test recognition`)
- [ ] 3.2 [complex] `image.read-header` reads a TIFF's first image width and length through a new `tiff_ifd.rs` directory reader (classic and BigTIFF, both byte orders, at most 4,096 entries, value arrays of at most 64 entries), with `CandidateReader` moved to `reader.rs`. It proposes `image.format` `TIFF` and the width and height whatever the color type or compression, and fails with `the TIFF header could not be read` for a file that ends after its signature, a first directory with no width, and a first directory past the end of the file. `image.format` is declared at version 2 with `PNG`, `JPEG`, `TIFF`. New tests in `packs/image/tests/tiff_header.rs` cover every TIFF scenario of asset-facets "The image pack records an image's format and pixel dimensions" and "A header that cannot be read fails the header run"; the schema test in `tests/header.rs` expects version 2 and three allowed values; the PNG and JPEG header tests still pass (design decision 4; asset-facets "The image pack declares the format and pixel dimension facets") (verify: `cd server && deli -- cargo test -p sidereal-pack-image --test tiff_header`, then `deli -- cargo test -p sidereal-pack-image --test header`)
- [ ] 3.3 [complex] The image pack registers `image.make-preview` (`MAKE_PREVIEW`), which makes previews, lists no facets and proposes kind `image` and media type `image/jpeg`. For PNG and JPEG it checks each side against 65,535 and the decoded size against 536,870,912 bytes (a progressive JPEG adds 2 bytes per sample, found by its own marker walk under the 8 MiB limit) before it decodes, decodes with `png` (`EXPAND`, 16-bit kept) and zune-jpeg, and streams a quality-90 baseline 4:4:4 JPEG from `jpeg-encoder` through a row-by-row `ImageBuffer`, in chunks of at most 64 KiB to `write_preview`. Tests in `packs/image/tests/preview.rs` run `Registry::execute_operator` with a collecting `Output`, decode the preview, and cover the image-preview scenarios for PNG and JPEG: registration, same size, EXIF rotation ignored, progressive JPEG, the transparent PNG pixel within 8, the PNG and JPEG memory-limit failures, and the PNG and JPEG decode failures and unrecognized bytes, each with its spec reason (design decision 5; image-preview "The image pack registers a preview Operator", "A preview is an 8-bit JPEG of the whole image", "A preview needs at most 512 MiB of decoded pixels") (verify: `cd server && deli -- cargo test -p sidereal-pack-image --test preview`, then `deli -- mise run check-server`)
- [ ] 3.4 [complex] The preview Operator makes previews of TIFF: it refuses with `the TIFF image type is not supported`, before decoding, every first image the spec does not list (CMYK, an alpha sample, JPEG compression, white-is-zero, planar samples, other sample sizes), checks the side and memory limits, and decodes with `tiff` (no default features; `lzw` and `deflate`) under `Limits { decoding_buffer_size: 536_870_912, .. }`. 16-bit samples become `v × 255 / 65535` rounded, decimals are clipped to 0–1 with not-a-number as 0, and a grayscale TIFF gives a one-component JPEG. Tests in `packs/image/tests/preview.rs` cover every TIFF scenario of image-preview, including the BigTIFF big-endian Deflate file, the tiled LZW file with a predictor, the several-images file, the 16-bit and decimal pixel values within 8, the 70,000-pixel side, the 15,000 by 6,000 16-bit file failing on memory with no pixel read, and the exactly-at-limit file failing on decoding. `tests/memory.rs` gains preview cases for a 16-bit RGB TIFF, a progressive JPEG and an RGBA PNG that assert the peak held is at most the decoded size plus 64 MiB (design decision 5 and its first risk; image-preview "The preview Operator decodes PNG, JPEG and these TIFF types", "Sample values are scaled to 8-bit with no brightening", "An image the Operator cannot decode fails the preview run") (verify: `cd server && deli -- cargo test -p sidereal-pack-image --test preview tiff`, then `deli -- cargo test -p sidereal-pack-image --test memory`, then `deli -- mise run check-server`)

## 4. Upload and the Asset routes [depends-on: 2, 3]

- [ ] 4.1 [complex] Upload runs `[FILE_SIZE, READ_HEADER, MAKE_PREVIEW]` in order, holding a one-permit semaphore around the preview run only, and every Asset entry has `preview_url`: `/api/assets/<id>/preview` or `null`. The 415 body reads `unsupported format: only PNG, JPEG and TIFF images are supported`. Tests in `server/tests/assets.rs` named `upload_…` and `preview_…` show: an 8-bit RGB TIFF of 800 by 600 answers 201 with `preview_url` set, `image.format` `TIFF` and its dimensions, and one `succeeded` preview run started by the uploader; `nebula.png` gets a JPEG preview; the runs end in order; a CMYK TIFF answers 201 with `preview_url` `null` and a `failed` run with `the TIFF image type is not supported`; a 409 runs nothing; the preview's version has no operation run; the disconnect tests expect three `succeeded` runs and a `preview_url`; the production-Registry unit test in `server/src/assets.rs` expects all three Operators (design decision 6; image-upload "Upload makes a preview of each new image", "A failed Operator run does not fail the upload", "A client that goes away does not stop the save or the run"; image-preview "A preview gets no runs of its own") — needs the database fixture (verify: `cd server && deli -- cargo test -p sidereal-server --test assets upload`, then `deli -- cargo test -p sidereal-server --test assets preview`, then `deli -- cargo test -p sidereal-server --test assets disconnect`)
- [ ] 4.2 [medium] `GET /api/assets/{id}/preview` streams the preview's bytes through the helper it shares with `/original`, with Content-Type `image/jpeg`, `X-Content-Type-Options: nosniff` and `Cache-Control: no-store`; it answers 404 for an unknown or malformed id, a derived id and an original with no preview, 503 before the body when the preview's object is missing, and ends the body early when a read fails after it started. `GET /api/assets`, `GET /api/assets/{id}` and `/original` list or answer only originals, so a preview's id is 404 on each; uploading a preview's bytes answers 201 with a new original; a request with no session gets 401 and no bytes. Tests in `server/tests/assets.rs` named `preview_route_…` and `originals_…` cover every asset-library scenario this change adds or modifies (design decisions 3 and 6) — needs the database fixture (verify: `cd server && deli -- cargo test -p sidereal-server --test assets preview_route`, then `deli -- cargo test -p sidereal-server --test assets originals`, then `deli -- cargo test -p sidereal-server`)
