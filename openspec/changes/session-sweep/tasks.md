## 2. The sweep task [depends-on: 1]

- [x] 2.1 [easy] `Schedule::HOURLY` in a new `server/crates/server/src/access/sweep.rs` is `first` 60 seconds and `every` 3600 seconds, and nothing reads either from the environment. A unit test in that file pins both values (verify: cd server && cargo test -p sidereal-server --lib access::sweep) (✓ cd server && cargo test -p sidereal-server --lib access::sweep passed)
- [x] 2.2 [medium] `sweep(database, schedule, log)` spawns a task that deletes expired rows at its first tick, `schedule.first` after it starts, and not before. In a new `server/crates/server/tests/sweep.rs` that uses `TestDatabase` as `tests/siderealctl.rs` does: with a schedule of a few hundred milliseconds, one expired row and one unexpired row, the expired row is still there right after the task starts, and once the first tick has passed only the unexpired row is left. The loop uses `interval_at` with `MissedTickBehavior::Delay`, as design says (verify: cd server && cargo test -p sidereal-server --test sweep first) (✓ cd server && cargo test -p sidereal-server --test sweep first passed)
- [x] 2.3 [easy] The task sweeps again every `schedule.every`: a row whose expiry is moved into the past after the first tick is gone after the next one (verify: cd server && cargo test -p sidereal-server --test sweep again) (✓ cd server && cargo test -p sidereal-server --test sweep again passed)
- [x] 2.4 [medium] A sweep that deletes rows writes exactly one line through its `Log`: `session sweep: deleted 3 expired sessions` for three rows, and `session sweep: deleted 1 expired session` for one. A sweep that deletes nothing writes no line. Capture lines with a `Lines` helper like the one in `tests/siderealctl.rs`. Give `Log` a crate-visible way to write a plain line, and widen its doc comment from security events to the server's log lines (verify: cd server && cargo test -p sidereal-server --test sweep line) (✓ cd server && cargo test -p sidereal-server --test sweep line passed)
- [x] 2.5 [complex] A sweep that cannot reach PostgreSQL writes exactly one line, `database unavailable: cannot sweep expired sessions; trying again in an hour`, and the task keeps running. Cause the outage as `relay_listens_again_after_the_database_refuses_it_for_a_while` does: `initialize` with a 1-second startup timeout, `ALTER DATABASE … CONNECTION LIMIT 0`, then end the database's other backends except the test's own. Set the schedule so the first tick falls inside the outage and the next tick falls after the test ends, so exactly one sweep fails. While the outage lasts, the task's `JoinHandle` is not finished and `GET /healthz` on `app_with_database` with the same `Database` answers 200 (verify: cd server && cargo test -p sidereal-server --test sweep unavailable) (✓ cd server && cargo test -p sidereal-server --test sweep unavailable passed)
- [ ] 2.6 [medium] After a failed sweep, once PostgreSQL accepts connections again, the next tick deletes an expired row. The test waits until the `database unavailable:` line is captured before it sets `CONNECTION LIMIT -1`, because a failed sweep waits up to the pool's acquire timeout (verify: cd server && cargo test -p sidereal-server --test sweep recovers)
- [ ] 2.7 [easy] Once `Database::close` has run, the task ends at its next tick or failed sweep and writes no line, so a graceful shutdown never logs `database unavailable:` from the sweep.
