## 3. The server's events [depends-on: 2]

- [x] 3.1 [medium] `Tuning` gains a `log: Log` sink whose default writes to stderr, and `access::routes` adds it as an `Extension` (design D-5). A browser claim answered 201 writes exactly one `security event:` line and one `instance_claim` row with source `http`, the client address and the user agent. A claim whose row is refused answers 503 `{"error":"unavailable"}` with an empty `users` table and no line. A claim answered 400 or 409 writes no line and no row. Tests live in a new `security_events` module in `tests/access.rs` (verify: cd server && cargo test -p sidereal-server --test access security_events::claim) (✓ cd server && cargo test -p sidereal-server --test access security_events::claim passed: 7 passed)
- [x] 3.2 [medium] A sign-in answered 200 writes one `sign_in`/`success` line with the matched username and no row. A sign-out answered 204 writes one `sign_out`/`success` line and no row. A sign-out answered 401, with no cookie, writes no line (design D-7) (verify: cd server && cargo test -p sidereal-server --test access security_events::session) (✓ cd server && cargo test -p sidereal-server --test access security_events::session passed: 5 passed)
- [x] 3.3 [complex] A sign-in answered 401 records one `sign_in`/`wrong_credentials` row before it answers, and writes one line, both with no username for a known or an unknown username, and with no `client_address` when the address is unresolved (design D-6). The user agent is the first 256 characters of the header, with invalid UTF-8 bytes as U+FFFD, the same in the row and the line (design D-3). When a trigger refuses the row, the answer is still 401 with the same body, and the line is written. A malformed body (400) writes nothing. A second router on the same database answers 200 to the address while the earlier rows remain (verify: cd server && cargo test -p sidereal-server --test access security_events::sign_in_fails) (✓ cd server && cargo test -p sidereal-server --test access security_events::sign_in_fails passed: 10 passed)
- [x] 3.4 [complex] The first 429 of a run, on both refusing paths, records one `sign_in`/`limited` row and writes one line with `client_address` and `retry_after` in place of `sign-in limited:` (design D-6). Later 429s of the run write nothing. Ten wrong sign-ins at the same moment leave exactly one `wrong_credentials` row and one `limited` row. A refused row still answers 429 with `Retry-After` and writes the line. The `sign_in_limit` and `spawned_sign_in_limit` tests expect the new line from the real process stderr. - 2026-11-14, task 4.1: `siderealctl` prompts written to a pipe never ended their line, so the event line followed `Repeat password: ` and did not start a line, as the spec requires. `Console` in `siderealctl/terminal.rs` now ends an open prompt's line after its answer is read when stdin is not a terminal. Prompts on a terminal are unchanged, and `--password-stdin` writes no prompt, so nothing changes there. Through a pipe, stderr now reads `Username: \nNew password: \nRepeat password: \n` before the event line.
