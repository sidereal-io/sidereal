## 1. The event and its line

- [x] 1.1 [medium] A new `core::access::security_event` module holds `SecurityEvent`, `Kind`, `Outcome` and `Source` (design D-1). Its `Display` writes `security event:` and the fields in the order `kind`, `outcome`, `source`, `username`, `client_address`, `user_agent`, `sessions_ended`, `retry_after`, leaving out each `None`. `username` and `user_agent` are quoted, with `\` as `\\`, `"` as `\"` and every control character as `\u{<hex>}` (design D-2). Unit tests pin the spec's example lines, a line feed in a username, a tab in a user agent, and `sa"m\` (verify: cd server && cargo test -p sidereal-core --lib security_event) (✓ cd server && cargo test -p sidereal-core --lib security_event passed: 10 passed)
- [x] 1.2 [medium] The table is gone: migration `4_security_events.sql`, `schema/4.json` and its entry in `baselines()` are deleted, and so is `Database::record` with its tests (brainstorm D1). The startup tests count three migration records again, list `sidereal_metadata`, `_sqlx_migrations`, `users` and `sessions` as the only application tables, and no longer have an upgrade-from-three-migrations test (verify: cd server && cargo test -p sidereal-core --lib startup && cargo test -p sidereal-core --lib security_event) (✓ cd server && cargo test -p sidereal-core --lib startup && cargo test -p sidereal-core --lib security_event passed: 24 and 9 passed)

## 2. Claim and reset return their event [depends-on: 1]

- [ ] 2.1 [complex] `Database::claim(username, password, source)` returns `Claimed { user, event }` and writes no event row (design D-4). A `Source::Http` claim inserts the user with one statement and sends nothing. A `Source::Siderealctl` claim inserts the user and sends the event's line with `pg_notify('sidereal_security_event', $1)` in one transaction (design D-10). A unique violation stays `ClaimError::Claimed` and sends nothing. Ten concurrent claims still create one administrator. A test listening on the channel receives exactly the line for a `siderealctl` claim, and nothing for an `http` claim. The `security_events` trigger tests are removed (verify: cd server && cargo test -p sidereal-core --lib access::claim && cargo check -p sidereal-server --all-targets)
- [ ] 2.2 [medium] `Database::reset_admin_password` returns `Reset` with its `access_recovery` event and sends the event's line with `pg_notify` in its existing transaction, with no insert (design D-4, D-10). When a trigger on `users` refuses the hash update, the reset fails as unavailable, the hash and every session are unchanged, and a listener on the channel receives nothing (verify: cd server && cargo test -p sidereal-core --lib access::recovery)
- [ ] 2.3 [medium] `Database::security_event_lines()` listens on `sidereal_security_event` and yields each payload that starts with `security event: kind=instance_claim outcome=success source=siderealctl` or the same with `kind=access_recovery`, and holds no control character. It listens through a new one-connection `listener` pool in `Database`, not the operational pool. It drops a payload of `forged`, a `kind=sign_in` line with `source=http`, and a `siderealctl` line that holds a line feed (design D-10) (verify: cd server && cargo test -p sidereal-core --lib security_event)

## 3. The server's events [depends-on: 2]

- [ ] 3.1 [medium] A browser claim answered 201 writes exactly one `security event:` line with `kind=instance_claim`, `source=http`, the client address and the user agent, through the `log` sink in `Tuning` (design D-5). A claim answered 400 or 409 writes no line. The tests that expected a row or a 503 for a refused row are removed. Tests live in the `security_events` module in `tests/access.rs` (verify: cd server && cargo test -p sidereal-server --test access security_events::claim)
- [x] 3.2 [medium] A sign-in answered 200 writes one `sign_in`/`success` line with the matched username. A sign-out answered 204 writes one `sign_out`/`success` line. A sign-out answered 401, with no cookie, writes no line (design D-7) (verify: cd server && cargo test -p sidereal-server --test access security_events::session) (✓ cd server && cargo test -p sidereal-server --test access security_events::session passed: 5 passed)
- [ ] 3.3 [complex] A sign-in answered 401 writes one `sign_in`/`wrong_credentials` line before it answers, with no username for a known or an unknown username, and with no `client_address` when the address is unresolved (design D-6). It makes no database write for the event. The user agent is the first 256 characters of the header, with invalid UTF-8 bytes as U+FFFD (design D-3). A malformed body (400) writes nothing. The tests that read or refused a `security_events` row are removed (verify: cd server && cargo test -p sidereal-server --test access security_events::sign_in_fails)
- [ ] 3.4 [complex] The first 429 of a run, on both refusing paths, writes one `sign_in`/`limited` line with `client_address` and `retry_after` in place of `sign-in limited:`, and `limited()` touches no database (design D-6). Later 429s of the run write nothing. Ten wrong sign-ins at the same moment write exactly one `wrong_credentials` line and one `limited` line. The `sign_in_limit` and `spawned_sign_in_limit` tests expect the new line from the real process stderr. They count only lines that start with `security event:` and hold `outcome=limited`, because each earlier 401 also writes a `security event:` line. No line starts with `sign-in limited:`. The row tests `sign_in_limit_concurrent_attempts_keep_one_row_of_each_outcome`, `sign_in_limit_keeps_one_limited_row_for_a_run_of_refusals` and `sign_in_limit_answers_429_when_its_row_is_refused` are removed, with the `security_events` module's row reader and `refuse` trigger helper once nothing uses them (verify: cd server && cargo test -p sidereal-server --test access sign_in_limit)
- [ ] 3.5 [complex] `main.rs` starts the relay after migrations and before `axum::serve`: a task that writes each line from `Database::security_event_lines()` to the `Log` sink (design D-10). The relay is a public function, so tests can start it with a capturing sink. In a new `relay` module in `tests/siderealctl.rs`, with the relay running against the test database, a `siderealctl` reset of a user signed in once makes the sink hold exactly the spec's line with `sessions_ended=1`. A `siderealctl` create makes it hold one `instance_claim` line with `source=siderealctl`. A raw `NOTIFY sidereal_security_event` of `forged`, or of a `kind=sign_in` line with `source=http`, adds nothing (verify: cd server && cargo test -p sidereal-server --test siderealctl relay)

## 4. The events from the box [depends-on: 2]
