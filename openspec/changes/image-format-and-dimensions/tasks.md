- [x] 3.2 [medium] `packs/image` depends on the `png` crate 0.18, and not on `image`, and `server/scripts/check-arch.sh` still passes. `image.read-header`, run through `Registry::execute_operator` over in-memory bytes, reads PNG dimensions with `png::Decoder::new(…)` and `read_header_info()`, through a `CandidateReader` that keeps the last two 64 KiB `read_candidate` windows. It proposes `image.format` `PNG`, `image.width` 4096 and `image.height` 2160 for a PNG whose `IHDR` gives 4,096 by 2,160 (the test bytes need only the signature and a valid `IHDR`, with no `IDAT`). A PNG of 200,000 `tEXt` chunks of 14 bytes each after a valid 640 by 480 `IHDR` succeeds with 640 and 480, and a test candidate that counts `read_candidate` calls shows 1 read. It gives the same answer over a test candidate that returns at most 3 bytes per read; this checks correctness only, and the bound on reads in 3.3 assumes full reads. It fails with `the PNG header could not be read` for the 8-byte signature alone; for a first chunk other than a 13-byte `IHDR`; for the 4,096 by 2,160 test bytes with only their `IHDR` CRC changed, while the unchanged bytes succeed in the same test; for a header cut off inside `IHDR`; and for a width or height of 0. It fails with `the image format is not recognized` for bytes that start with neither signature (design decision 5; asset-facets "The image pack records an image's format and pixel dimensions" PNG scenario, "A header that cannot be read fails the header run") (verify: `cd server && deli -- cargo test -p sidereal-pack-image --test header png`, then `deli -- mise run check-server`) (✓ `cargo test -p sidereal-pack-image --test header png` passed, 11 tests; `mise run check-server` passed, arch lint ok)
- [ ] 3.3 [complex] `packs/image` depends on `zune-jpeg` 0.5, and `image.read-header` reads JPEG headers with `zune_jpeg::JpegDecoder::new_with_options` over the `CandidateReader`, with the width and height limits raised to 65,535, then `decode_headers()`. For a JPEG, `CandidateReader` treats the candidate as ending after 8,388,608 bytes (8 MiB) and never asks for a byte past that point. It proposes `JPEG` with the frame header's width and height for: a baseline (`0xC0`) JPEG of 6,000 by 4,000; a progressive (`0xC2`) JPEG of 1,920 by 1,080; a baseline JPEG of 20,000 by 12,000, above zune-jpeg's default limit; a JPEG with a 60,000-byte `APP1` EXIF segment and an `APP2` ICC segment before its frame header; and a JPEG whose EXIF orientation says to rotate 90 degrees, which still gives 6000 by 4000. It fails with `the JPEG header could not be read` when it reaches start-of-scan or end-of-image before a frame header, when the bytes end inside a segment, for a lossless (`0xC3`) frame header of 640 by 480 (zune-jpeg skips it as unknown and reaches start-of-scan with no supported frame header), for a 12-bit `SOF1` (`0xC1`) frame header of 640 by 480, for a width or height of 0, for a JPEG with 9 MiB of `APP2` ICC segments before a 640 by 480 frame header, and for a JPEG of 19-byte `APP2` ICC segments that fill the first 8 MiB before a 640 by 480 frame header; for both, a counting candidate shows no read reaches past 8 MiB. At the limit: a 640 by 480 JPEG whose first start-of-scan segment ends exactly at byte 8,388,608 succeeds, and the same JPEG with that segment ending at byte 8,388,609 fails with `the JPEG header could not be read`. A test candidate that returns full windows and counts `read_candidate` calls shows the bound on reads: a crafted JPEG of about 4 MiB of 4-byte segments and `0xFF` fill bytes before its frame header, and one of 64 `APP1` EXIF segments of 65,533 bytes each before its frame header, each cost at most `min(size, 8 MiB) / 65,536 + 4` reads and still yield their dimensions; a 4 MiB JPEG whose start-of-scan lies in its first 64 KiB costs at most 2 reads, so the run never reads the whole file; and a run whose host reports cancellation fails without reading the rest of the candidate (design decision 5; asset-facets "The image pack records an image's format and pixel dimensions" JPEG scenarios, "A header that cannot be read fails the header run", "The header Operator reads at most 8 MiB of a JPEG") (verify: `cd server && deli -- cargo test -p sidereal-pack-image --test header jpeg`, then `deli -- mise run check-server`)

## Deviations Ledger

- **2.1 writes a choice's allowed values into the new `facet_schemas` row.**
  Task 2.2 names this, but migration 6's check refuses a `choice` row with
  no allowed values, so 2.1 could not store `PNG` without it. 2.2 adds the
  comparison with the kept row and its tests.
- **A refused choice's reason leaves out the proposed text.** It reads
  `facet <name> is a choice of PNG, JPEG, and the text is none of them`, so
  an Operator's unbounded text never lands in the run's reason.
- **The header Operator also fails a PNG width or height above
  2,147,483,647.** Design decision 5 names this check; 3.2 tests it with
  `png_wider_or_taller_than_the_png_limit_fails`.
